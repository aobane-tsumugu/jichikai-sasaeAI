# fixtures: 試しのデータ

秋の収穫祭を段0から段6まで通す資料と、総会・役員会・当番・市の依頼の通しに使う試しのデータです。実在の自治会、人、事業所、自治体、資料を元にしていません。写真に見える画像も、プログラムで作った合成で、実際に撮った写真でも、実際の手書きでもありません。通し方は [docs/RUNBOOK.md](../docs/RUNBOOK.md) にあります。

ささえ台自治会に送るデモ資料25点（関係する資料と関係のない資料を混ぜ、中身が少しだけ違う版の組を三つ入れた物）は、[sasaedai/](sasaedai/README.md) にあります。

去年は 2025 年 10 月 25 日（土）、今年は 2026 年 10 月 24 日（土）の祭りで、雨で会場が変わる前日は 10 月 23 日（金）です。

行事の資料内の「今年」はこの固定した年です。種類ごとの資料の年は後の表に記します。2026年11月6日には開催日も答えの締切（10月9日）も過ぎています。これから出欠や手伝いを試すときは、元の資料を変えず、別の確認用の行事を開き、試用する開催日・案内と募集の締切を実行日より後の日として手入力します。過去の内容を自動で今年の決定にしたとは扱いません。日付の入力例と、閉じた受付の開き直しは[RUNBOOKの試用手順](../docs/RUNBOOK.md)を参照してください。

## 作り方

上の表にある`roster/`、`last-year/`、`this-year/`と`kinds/`の資料は、`build/`のスクリプトで作っています。名簿、Word、Excel、PDF、合成画像、メモの文、Web回答とLINEのJSONが対象です。下のコードによる検証用データは別に手書きしています。

```bash
python -m pip install -r fixtures/build/requirements.txt
python fixtures/build/build_fixtures.py
```

- `build/build_fixtures.py`が上の資料の中身を持っています（名簿、文、表、画像、Web回答とLINEのJSON）。`build/paper.py`が紙の写真風と手書き風の部品です。
- 手書き風の文字は、教科書体の字体で一字ずつ大きさと傾きと位置をずらして書き、線と丸は揺らして引いています。紙の写真風は、机の上に斜めに置いて台形に歪め、影と明るさのむらと粒を足した物です。
- 乱数の種は固定してあり、画像、PDF、文は作り直しても同じ物ができます（Word と Excel は中身が同じで、ファイルの日時だけ変わります）。
- 字体は Windows に入っている BIZ UD ゴシック、BIZ UD 明朝、UD デジタル教科書体を使います。字体のファイルはこのリポジトリに置いていません。他の環境では、環境変数 `FIXTURE_FONT_DIR` で同じ名前の字体のある場所を指します。
- 実在の資料は読み込みません。内容は全て、この作業のために書いた物です。

### 手書きの検証用データ

| 場所 | 来歴と使う範囲 |
|---|---|
| `first-slice.ts` | 試験用に書いた試しの資料・読み取り結果など。AIの代わりに使う値を含み、実際の読み取り成功の証拠ではありません |
| `provider-contact.ts` | 提供側への問い合わせの試験用に書いた試しの入力 |

通しが照合する文は`test/fixtures/kinds.ts`の`kindsMaterial()`と`scripts/walkthrough-meeting.ts`の`meetingMaterial()`から生成時に直接読みます。決定、未決、議案、世帯の名前、時間帯、持ち場は文の通しと共通です。表の名前と日付の基準は`test/fixtures/kinds-files.ts`にあります。生成にはPythonに加えてNode.jsを使います。

総会の準備と議事録作成を別の時点で試すため、指定の去年の3点に今年の資料と記録を足しています。役員会も2回目の記録を別にしています。去年の紙を今年の記録として送り直しません。

生成する日によって資料が変わらないよう、種類ごとの年は2026年、総会の日付を決める基準日は2026年11月7日に固定しています。総会の開催日は2027年1月6日、答えの締切は2026年12月7日です。過ぎた期限は受付が閉じるため、PMは実行日とこの日付を照合してください。ファイルを使わない通しは従来どおり実行日から決めます。

種類ごとの12点だけを生成するコマンドです。既存の行事の資料を作り直しません。

```powershell
python fixtures/build/build_fixtures.py --kinds
```

PMが確認用の試しの区へ流すときは、従来の引数に`--files`を付けます。`demoku`には流しません。

```text
npm run walkthrough-meeting -- --base <URL> --ward <試しの区のURL名> --creds <資格情報ファイル> --files
npm run walkthrough-kinds -- --base <URL> --ward <試しの区のURL名> --creds <資格情報ファイル> --files
```

`--files`は「送る」画面を開き、同じ画面のWord・Excelの展開処理で取り出した内容と元のファイルをmultipartで送ります。PDFと写真は元のバイトを送り、全ファイルの読み取りと反映を待ちます。フラグがないときの入力は従来の文のままです。HTTPで受付へ送る道具で、ブラウザのクリックや画面の見た目を確認するものではありません。

`test/kinds-files-intake.test.ts`の主な流れ1本は、12点の存在、実ファイルの展開、multipart受付、R2への保管と偽AIの読み取りを対象にします。本物のAIによる読解、種類ごとの配布までの通し、Word・Excel・PDFの実物の見え方、stagingでの実行は別の確認です。これらの成功を資料の生成だけからは主張しません。

- 本物の手書き、本物のスマホの写真での読み取りは確かめていません。合成の画像は読みやすい方に寄っています。実運用の精度とは別に考えます（報告に、本物の手書きが要る枚数を書いています）。
