# SasaeAIの設計（公開用）

自治会の役員が、手元の資料から準備を進め、住民に配り、実施後の記録を次の担い手へ残すための運営支援システムです。この文書は2026年11月6日のmain（4a3b85a）にある構成を説明します。試用手順と確認結果は[README.md](../README.md)、操作の詳しい手順は[RUNBOOK.md](RUNBOOK.md)にあります。

## 1. 対象と考え方

行事、総会、役員会、当番、市からの依頼など、ひとまとまりの仕事をプロジェクトとして扱います。役員が持つ紙の写真、ファイル、電話や立ち話のメモを、元の資料を残したまま同じ仕事につなぎます。最初に端から端まで確かめた題材は、架空の秋の収穫祭です。

役員に資料の事前分類、マスキング、保存先の判断、AIの全件点検を求めない設計です。AIは読み取りや下書きを支援し、役員が運営上の判断と配る操作を行います。質問が残っているだけで、ほかの仕事を止めません。

住民は登録せずに案内を読んで答えられ、AIと会話しません。紙とWebは同じ配った内容から作ります。印刷、配達、回覧、設営、当日の運営や人との調整は残ります。負担がどの程度変わるかは測定していません。

## 2. 画面と情報の範囲

| 場所 | 使う人と仕事 | 扱う情報 |
|---|---|---|
| 役員画面 | 資料を送り、段取りや質問を見て、下書きを直して配る | 元の資料、今年の中身、参考資料、答え、運営メモ |
| 区のページ | 住民が案内と変更を読み、出欠や手伝いを答える | 人が配った公開用の文書。答えや名簿は公開しない |
| 実行委員と班長のページ | 配られた作業資料を読み、書き込んだ紙を送る | 配った文書と表、届いた写真。班長用の入口は自分の班の答えを扱う |
| 提供側の運用画面 | 区の開設、入り方の支援、問い合わせ対応、保守 | 運用に必要な設定と記録 |

役名の表示だけを鍵にしません。役員の認証、実行委員と班長の合言葉や一人用の入口、提供側の認証を使い分けます。区のデータはward_idで分けて読み書きします。

### 役員の入り方と問い合わせ

IDとパスワード、LINE、メールの入口を持ちます。LINEとメールは設定済みの場合だけ表示します。役員が出す一人用の入口は一度だけ7日間、提供側の再発行は一度だけ24時間使えます。再発行で前のリンクとパスワードを使えなくしても、LINE・メールの接続や覚えた端末は残す作りです。

入れないときは別の入り方やほかの役員を試し、解決しないときは提供側への問い合わせを使います。問い合わせには連絡できるメールアドレスを使い、受付番号を入力して入る入口は設けません。提供側は本人をどう確かめたかを残してから入り方を作り直します。メール送信やLINEで入る機能の実運用は、外部連携の設定と確認が別に必要です。

## 3. 記録する物

- **プロジェクト:** 行事など、一つの仕事の場です。種類別の段取りを用意し、仕事、時期、担当を必要なところだけ直せます。
- **元の資料:** 送られた写真、ファイル、文を受け取ったときの形で残します。
- **読み取った内容:** 元の資料の文字や表、出どころを記録します。AIが推測したことと、人が入れたことを分けます。
- **今年の中身と参考:** 去年の担当や金額、年が分からない資料を、今年決まったこととして扱いません。食い違いや必要な確認を質問にします。
- **下書き:** 案内、募集、当番表、進め方、変更の知らせ、報告を人が直せます。保存だけでは配られません。
- **配ったもの:** 配った時点の文書と表を残します。あとで下書きを直しても、配り直すまで住民や実行委員に見える内容は変わりません。
- **答えと運営メモ:** 世帯の答え、手伝い、来年に残すことを記録します。運営メモは会計帳簿や決算を置き換えません。

閉じた仕事は、元の資料、配ったもの、報告、段取り、答えの集計を読み返し、新しい年の準備に使います。

## 4. 資料から配布まで

1. 写真、ファイル、短い文を受け取り、元の資料を保存します。
2. 写真やPDFを読み取り、対象の行事を選びます。分からないものは「届いたもの」に残します。
3. 既存の内容と照らし、変わったところや質問を記録します。
4. 役員が必要な下書きを作り、直します。紙の見え方もここで開けます。
5. 人が配る操作をすると、その時点の内容を保存し、公開ページや実行委員と班長のページ、印刷用ページに出します。
6. 紙、Web、電話などの答えを受け、変更があれば直して配り直します。
7. 実施後に報告を書いて閉じ、記録から次の仕事を始めます。

紙のQRや紙の番号は、元の行事と配った内容に戻るために使います。下書きの紙は配った紙と区別します。紙の内容をHTTPで確認した結果と、刷った実物や写真からの読み取りは別の確認です。

## 5. Claudeが行う仕事

### 読む処理とつなぐ処理

写真やPDFの読み取りは、Anthropic Messages APIへの一回の呼び出しで、決めた形式の結果を得ます。読み取った内容をプロジェクトの状態につなぐ仕事、下書きや報告を作る仕事にはClaude Managed Agentsを使います。

Managed Agentsには、MCP経由で次の五つの手を渡します。

- 開いているプロジェクトを引く
- プロジェクトの状態を引く
- 読み取りを引く
- 差分を書く
- 質問を書く

入力や仕事ごとに短いセッションを開き、前の会話を持ち越す代わりに保存した状態を読みます。エージェントには元の資料そのもの、自由なファイル操作やシェル、配布を決める操作を渡しません。資料の中の文は、AIへの指示ではなく資料として扱います。

### モデルと認証

読み取り、接続、下書きにはclaude-sonnet-5-5、候補から行事を選ぶ処理にはclaude-haiku-5-5を使います。製品内ではOpusを使いません。認証はWorkload Identity Federationで短期間のトークンを得る構成です。

[読み取り](../src/ai/read.ts)、[セッション](../src/ai/session.ts)、[MCP](../src/ai/mcp.ts)、[モデルと認証](../src/ai/anthropic.ts)に実装があります。これらの実装があることと、すべての入力で正しく動くことは区別します。

### AIが使えないとき

配った案内、答えの受付、記録、印刷は保存済みの内容を使います。役員は手で下書きを直して配ることもできます。AIの停止中にもこれらを使える構成ですが、障害を含む全体の実運用の確認は完了していません。

## 6. 公式LINE、答え、写真

公式LINEは提供側が区ごとに用意し、受け付けと通知に使います。住民がWebや紙で答えるために、友だち追加を必須にはしません。公式LINEの一斉送信を使わずに区のページと紙へ配ることもできます。

写真の当て先は、紙のQRや番号、公式の質問への答え、撮り直しの対応がある場合は、その事実で決めます。送られた場所、直前の写真、時期だけでは決めません。AIによる判断では、同じトークの前30分の文と写真（合わせて20件まで）、後10分の文、開いている行事の仕事と日付を比べます。自信がなければ「届いたもの」に残し、後続の文を待っても分からない場合は写真を引用して一問聞きます。

前後の文は写真の当て先を考えるために一時的に使い、判断後に消します。別の未解決の写真にも必要な文はその判断まで、長くても1日を上限に保持する作りです。別のトークの文は使いません。写真の受け付けと保存はAIの判断失敗でも残します。

世帯の答えと作業の連絡を分け、問い合わせへの回答は役員が行います。AIが住民への返事を作ったり、運営上の判断を代わりに行ったりしません。本物のLINEでの文と写真の受信記録はありますが、グループや質問・返事を含む全体の実機確認は別に必要です。

基準のmainでは、写真は実行委員と班長のページおよび役員の範囲で扱います。顔を自動で隠して公開する部品は未実装で、公開写真の安全性を検証済みとはしません。

## 7. 基盤、保管、復旧

| 技術 | 役割 |
|---|---|
| TypeScript、Cloudflare Workers、Hono | 画面、API、受付と処理。WorkersがHTMLを返す |
| Cloudflare D1 | 行事の状態、答え、配布記録などを保管する |
| Cloudflare R2 | 元の資料と日次の写しなどを保管する |
| Anthropic Messages API、Managed Agents | 読み取り、状態への接続、質問と下書き |
| LINE Messaging API | 文や写真の受け付け、通知と役員からの返事 |

日次の写し、区の書き出し、消去の処理があります。写しのJSONと、R2にある元の資料ファイルは別のものです。復旧には両方の保管と確認が必要で、写しを作る処理があるだけで復旧できると断定しません。実際のD1・R2への復旧は未確認です。

個人情報の利用目的、委託の根拠と契約、閲覧範囲、保管期間、バックアップ、削除、障害対応は、提供側が実運用の前に確認して自治会に説明する必要があります。基盤の採用やローカル試験の通過だけで、運用上の適法性や安全性を保証しません。
