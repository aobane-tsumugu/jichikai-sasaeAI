# 設計書（公開用）

この文書は自治会運営AI支援（仮称）の公開できる設計要点をまとめたものです。設計には構想・未実装の項目が含まれます。実装と確認の現在地は [README.md](../README.md) と [STATE.md](STATE.md) を参照してください。ここでは特定の自治体や個人に関する情報を扱いません。

## 序. この設計書が答えること

本システムは、自治会の行事や総会などをプロジェクト単位の仕事の場として扱います。紙の写真、ファイル、短いメモなどが入るたびに、AI が既存の状態と照らし、関係する項目、変わった点、古くなりそうな文書、確認の問いを提示します。原本を残し、読み取りや提案は出どころを参照できる記録として扱います。配布する内容を決めるのは人です。

実現方法は機能ごとに選びます。Workers の決定的な処理、一回の API 呼び出し、仕事ごとの指示とデータ形式、手を使って複数段を進める Managed Agents を使い分けます。プロジェクトの空間、そこでできる仕事、裏側の AI の動作を一組として設計します。

## 1. 運営支援システムは何か

自治会役員の事務作業をプロジェクトごとに扱い、入った資料を既存の状態につなぐシステムです。案内や募集、出欠、当番表、変更、報告などを同じ場で扱い、原本、今の状態、確認事項、下書き、配布した内容を結び付けます。

紙と Web の案内は同じ配布内容から作ることを目指します。住民は登録せずに公開ページを読めます。AI は準備を支援しますが、AI の推定は正式な決定にならず、配布の判断は役員が行います。紙の配達、会場設営、当日の運営、人との調整などは残ります。

## 2. 登場する物

### 2.1 システムの部品

| 部品 | 役割 |
|---|---|
| 役員画面 | 資料を送り、状態や確認事項を見て、案を直して配布する |
| 区のページ | 配布済みの案内、変更、報告を公開し、回答を受け付ける |
| プロジェクトの空間 | 実行委員や班長が行事のための資料を見て送る |
| 運用の画面 | 提供側が開設や運用を行う |
| 公式 LINE | 任意の通知や受け付けに使う連携先 |
| AI | 資料を読み、状態につなぎ、確認事項や下書きを提示する |
| 記録 | 原本、読み取り、状態、配布物、終了後の記録を保管する |
| 紙 | ブラウザから印刷する案内や回答票などを扱う |

### 2.2 情報の単位

- **プロジェクト:** 行事や総会など、ひとまとまりの仕事です。
- **原本:** 送られた写真、ファイル、文など、受け取った時の資料です。
- **読み取り・提案:** 原本から得た文字や情報、状態への提案です。元の資料と出どころをたどれるようにします。
- **配布した内容:** 役員が確認して配った内容です。後から変更しても、過去の配布分を区別できるようにします。
- **地図:** 仕事の順序、関係者、出来事、次の確認点をまとめ、進行と引き継ぎを助ける構想上の表示です。

## 3. 画面と機能

### 3.1 役員画面

役員は資料を送る、読み取りとその影響を見る、問いに答える、案を直す、配る、回答を確認する、印刷する、過去の記録から次のプロジェクトを始める、といった操作をします。プロジェクトごとの地図に、時系列、仕事、決めたこと、資料、配布物を結び付けて表示することを目指します。役員に資料の事前分類、マスキング、保存先の選択、AI の全件点検を求めない設計です。

### 3.2 プロジェクトの空間

実行委員や班長が、担当するプロジェクトの資料、当番表、配置図などを見たり、書き込みのある資料を送ったりする場所です。閲覧範囲と終了後の扱いを制御します。

### 3.3 区のページと運用の画面

区のページは、配布済みの案内や変更、報告を登録なしで読める公開ページです。回答の内容は公開せずに受け付ける想定です。運用の画面は、提供側が区の開設やシステムの保守を行う画面です。

## 4. プロジェクトの場でできること

1. プロジェクトを開き、前年の記録や一般的な仕事の型を参照する。
2. 役員、実行委員、班長が必要な範囲で入る。
3. 紙の写真、ファイル、一行のメモ、回答などを送る。
4. 状態、原本、読み取り、差分、問い、下書きを確認する。
5. 人が決定し、案を編集する。AI の提案だけで運営上の決定を確定しない。
6. 配布内容を公開ページ、印刷用ページなどから届け、必要に応じて変更版を作る。
7. 実施後に報告し、記録を閉じて、次の年のプロジェクトに引き継ぐ。

## 5. AI が裏でどう動くか

### 5.1 仕事に応じた方法

読み取りのように入力と出力が明確な仕事は Messages API の一回の呼び出しにします。資料を既存のプロジェクト状態につなぎ、差分や問いを記録する仕事は Managed Agents に任せます。候補からプロジェクトを選ぶ単純な処理は軽いモデルに分けます。全ての機能にエージェントを使うのではなく、仕事に合わせて方法を選びます。

### 5.2 資料を受け取ってからつなぐまで

1. Workers が原本を受け取り、保存と処理状況の管理を行います。
2. Messages API が写真や PDF を読み、決めた形式の読み取りを返します。
3. 入力ごとに Managed Agent のセッションを開き、対象プロジェクトの状態を参照します。
4. Agent は MCP 経由で五つの手を使います。開いているプロジェクトを引く、プロジェクトの状態を引く、読み取りを引く、差分を書く、問いを書く、です。
5. 出どころを持つ差分や問いを記録し、処理結果を役員画面に返します。
6. 役員が確認・修正し、配布する内容を決めます。

エージェントには原本そのものや、配布を決める操作を渡しません。短いセッションで一つの入力を扱い、過去の会話を持ち越さず、プロジェクトの状態と読み取りを参照する設計です。

### 5.3 状態、出どころ、版

AI の推定は出どころと確かさを伴う提案です。食い違いや不足は問いとして扱い、勝手に確定しません。役員が配布した内容をその時点の版として残し、変更後も以前の配布内容を参照できるようにします。

### 5.4 モデルと認証

`claude-sonnet-5-5` は資料の読み取りと既存状態への接続、`claude-haiku-5-5` は候補から選ぶ単純な処理に使います。製品内では Opus を使いません。Anthropic の固定 API キーはアプリやリポジトリに置かず、Workload Identity Federation で短期間のアクセストークンを得る構成です。認証情報の設定や管理は提供側の運用範囲です。

### 5.5 AI が使えない時

読み取りや提案が止まっても、人が手で案を作って配布でき、既に配布したページ、記録、印刷物、回答を使えることを目標にします。この動作を含む全体の実機確認は完了していません。

## 6. 入口と出口

### 6.1 入る物

- 役員が撮影する紙の写真や端末から送るファイル
- 電話や対面で聞いた結果を役員が記した短い文
- 公式 LINE を使う場合のメッセージや添付資料
- 住民から公開ページに届く回答
- 役員が代理で入力する回答

住民の回答は名簿の有無を表示せず、送られた内容として受け付ける方針です。受け付け方や実際の画面は検証が必要です。

### 6.2 出す物

- 公開ページの案内、変更、報告、回答フォーム
- プロジェクトの空間に共有する作業資料
- ブラウザから印刷する案内、回答票、当番表、配置図
- 公式 LINE を任意の通知手段として使う場合の題名と URL

紙と Web は同じ配布内容を元にする設計です。印刷、配達、掲示、当日の運営などの物理作業は残ります。

## 7. 権限と境界

### 7.1 閲覧範囲

設計上の範囲は、公開ページ、プロジェクトの空間、役員画面、提供側の運用画面です。回答の内容や名簿など公開しない情報は、公開ページから読めないようにします。役割名だけを認証の根拠にせず、ログインや招待などの仕組みで範囲を制御します。

### 7.2 個人情報、保管、削除

原本や名簿を扱う可能性があるため、情報の利用目的、委託先、閲覧範囲、保管期間、バックアップ、削除、障害対応をサービス提供側の責任範囲として設計します。Anthropic など外部基盤への委託の根拠と契約、実際のデータ保持、自治会への説明は実運用の前に確認が必要です。現時点で運用上の適法性や安全性を保証するものではありません。

## 8. 基盤と連携先

| 種類 | 想定する技術・連携 | 主な役割 |
|---|---|---|
| アプリ基盤 | Cloudflare Workers、Hono | 画面、API、処理の受付 |
| データ | Cloudflare D1、R2 | 状態、読み取り、原本、配布物の保管 |
| AI | Anthropic Messages API、Managed Agents | 資料の読み取り、状態への接続、問いや下書き |
| 任意の連携先 | LINE Messaging API | 受け付けや通知 |
| 認証 | Workload Identity Federation | 固定 API キーを置かずに短期トークンを取得 |

本番での保管場所、外部事業者との契約、費用、バックアップ、障害時の対応は提供側が確認・運用します。基盤や連携先の採用だけで、個人情報の取り扱い上の要件を満たしたとは扱いません。

## 9. 作る順

最初の一片は製品全体ではなく、秋の収穫祭という一つのプロジェクトを端から端まで通す順序上の試みです。

**最初に扱う範囲:** プロジェクトを開く、資料を受け取る、読み取りと接続、状態・差分・問い、案の作成と確認、配布、公開ページと印刷、回答、プロジェクトの空間、報告、終了後の記録を扱うための各部品。

**後に続ける範囲:** 年間の記録検索、行政への依頼の期限と提出、帳簿と決算、顔写真の公開前処理、対象者を絞った配布、画面上での当番表編集など。これらを含む製品全体が完成したとは示していません。

実装の有無や動作確認の段階は [STATE.md](STATE.md) に記録します。設計に記載があることだけでは、実装済み・実機確認済みとはみなしません。
