# SasaeAIの設計（公開用）

自治会の役員が、手元の資料から準備を進め、住民に知らせ、終わったあとの記録を次の担い手へ残すためのWebアプリです。この文書は2026年11月8日のmainの構成を説明します。試用手順と確認結果は[README.md](../README.md)、操作の詳しい手順は[RUNBOOK.md](RUNBOOK.md)にあります。

## 1. 対象と考え方

行事、総会、役員会、当番、市からの依頼など、ひとまとまりの仕事を一つの準備（コードではproject）として扱います。準備は自治会の一年の予定から始め、去年の同じ予定のやることと資料を引き継ぎます。役員やAIに準備の種類を分類させません。役員が持つ紙の写真、ファイル、役員のLINEグループの投稿、電話や立ち話のメモを、元の資料を残したまま同じ準備にまとめます。最初に端から端まで確かめた題材は、デモの秋の収穫祭です。

役員に資料の事前分類、マスキング、保存先の判断、AIの全件点検を求めない設計です。AIは読み取りや下書きを支援し、役員が運営上の判断と知らせる操作を行います。質問が残っているだけで、ほかの仕事を止めません。

住民は登録せずに案内を読んで返事ができ、AIと会話しません。紙とWebは同じ知らせた内容から作ります。印刷、配達、回覧、設営、当日の運営や人との調整は残ります。負担がどの程度変わるかは測定していません。

## 2. 画面と情報の範囲

| 場所 | 使う人と仕事 | 扱う情報 |
|---|---|---|
| 役員画面 | 資料を送り、やることや質問を見て、下書きを直して知らせる | 元の資料、今年の中身、参考資料、返事、運営メモ |
| 住民向けのページ | 住民が案内と変更を読み、出欠や手伝いを返す | 役員が知らせた公開用の文書。返事や名簿は公開しない |
| 実行委員と班長のページ | 役員が知らせた作業の資料を読み、書き込んだ紙を送る | 知らせた文書と表、届いた写真。班長用の入口は自分の班の返事を扱う |
| 運用の画面（SasaeAIの運営者が使う） | 自治会の開設、ログインの支援、問い合わせへの対応、保守 | 運用に必要な設定と記録 |
| 役員のLINEグループ | 自治会のLINEを入れたグループで、役員がいつもどおり投稿する | 入れたあとの投稿と写真。SasaeAIからの知らせ |
| 実行委員や班長のLINEグループ | 自治会のLINEを入れた場合に、同じように投稿が届く | 入れたあとの投稿と写真 |
| 自治会のLINEの個別のトーク | 住民や役員が質問や写真を送る。友だちに知らせが届く | 質問、写真、返事。受け取りの一言は決まった文で、返事は役員が書く |

役の名前だけで、見られる範囲を決めません。役員のログイン、実行委員と班長の合言葉や一人用の入口、運営者のログインを使い分けます。自治会のデータはward_id（自治会の識別子）で分けて読み書きします。

### 役員のログインの方法と問い合わせ

ログインの方法は、IDとパスワード、LINE、メールの三つです。LINEとメールは設定済みの場合だけ表示します。役員が出す一人用の入口は一度だけ7日間、運営者の再発行は一度だけ24時間使えます。再発行で前のリンクとパスワードを使えなくしても、LINE・メールの接続や、ログインを覚えている端末は残す作りです。

ログインできないときは、別のログインの方法を試すか、ほかの役員に頼み、解決しないときはSasaeAIの運営者への問い合わせを使います。問い合わせには連絡できるメールアドレスを使い、受付番号を入れてログインする入口は設けません。運営者は本人をどう確かめたかを残してから、ログインの方法を作り直します。メールの送信やLINEでログインする機能の実運用は、外部連携の設定と確認が別に必要です。

## 3. 記録する物

- **準備:** 行事など、一つの仕事の場です。去年の同じ予定のやること（記録がなければ一般的なやること）を引き継ぎ、仕事、時期、担当を必要なところだけ直せます。
- **元の資料:** 写真は長い辺が2400pxまでのJPEG（品質85を目安）に整えたもの、ほかのファイルと文は受け取ったときの形で残します。写真を整えられないときは届いた写真をそのまま残し、読めなかったところとして扱います。
- **読み取った内容:** 元の資料の文字や表、出どころを記録します。AIが推測したことと、人が入れたことを分けます。
- **今年の中身と過去の資料の中身:** 去年の担当や金額、年が分からない資料を、今年決まったこととして扱いません。食い違いや必要な確認を質問にします。
- **資料の日付と、中身が少し違う二つの資料:** WordとExcelの保存日、PDFの更新日、写真の撮影日を資料の日付として持ちます（役員には入れさせません）。中身が少しだけ違う二つの資料は、AIが一組につき一度だけ中身を比べ、違う所、中の手がかり、どちらが新しいかの推測を残します。去年の資料で日付と推測が同じ方を指すときはその方を参考に使い、理由を出どころに書きます。今年の中身の食い違いと、どちらか分からないときは、比べた結果を添えて役員に一度聞きます。後から届いた方で黙って上書きしません。
- **下書き:** 案内、募集、当番表、進め方、変更の知らせ、報告を人が直せます。保存しただけでは知らせません。
- **知らせたもの:** 知らせた時点の文書と表を残します。あとで下書きを直しても、知らせ直すまで住民や実行委員に見える内容は変わりません。
- **返事と運営メモ:** 世帯の出欠の返事、手伝いの申し出を記録します。運営メモには、準備ごとの金額、頼んだ相手、来年に残すことなど、分かることだけを書きます。運営メモは会計帳簿や決算を置き換えません。

終わった準備は、元の資料、知らせたもの、報告、やること、返事の集計を読み返し、新しい年の準備に使います。

### 種類ごとの資料と引き継ぎ

総会の返事は出席・委任・欠席を世帯で数えます。紙・Web・電話・LINEで同じ意味を使い、委任する相手が空欄なら推測せず空欄を残します。招集の紙には回答票・委任状を付け、議案の資料と議事録も残します。回答票への追記は知らせるときに文書へ保存し、住民の画面と再印刷は保存済みの追記を読みます。下書きのときだけ、今の自治会の設定（連絡先など）を使います。成立や委任の有効性は人が判断します。

役員会の議題では、同じ自治会の終わった前回の会議から、決定、未決、残った質問、議事録を読みます。未決の文やAIの下書きを決定へ置き換えません。総会の議案には年と出どころを保って会議の決定、運営メモの合計、行事の報告を渡します。運営メモは決算ではありません。[会議の資料](../src/draft/meeting-materials.tsx)で組み立てます。

当番は、去年の同じ当番の記録または届いた去年の表を今の名簿と照合し、転入・転出と期間つきの免除を反映した下書きを作ります。去年の表がないときは名簿から始めます。人が直した担当や知らせた表は、自動で書き換えません。免除は役員が理由と期間を記録して取り消せます。理由は役員の範囲に残し、住民向けのページ、実行委員と班長のページ、知らせる表には含めません。世帯ごとの当番・役・免除の履歴は[src/rota/](../src/rota/)で扱います。

実行委員名簿は名前・役・連絡先の表です。資料から読み取り、役員が人を足す・直す・外すことができます。去年の名簿をそのまま今年の名簿にせず、当番表や進め方を知らせるときの内容を保存します。知らせ直すまで実行委員と班長に届く名簿は変わらず、住民向けのページには出しません。[名簿の画面](../src/project/committee.tsx)と[知らせた表の記録](../src/space/publication-tables.ts)に実装があります。

### 住民向けのページの転送と、記録の検索

住民向けのページには、LINEなどで転送されたときに出る題・説明・画像と、正規のURLを付けます。説明には知らせた案内の日時・場所を使い、自由記述の本文や連絡先、返事をした人の名前を写しません。検索エンジン向けの一覧には、公開した内容だけを載せ、限られた人向けのもの、取り下げたもの、止めた自治会を除きます。[src/seo/](../src/seo/)の実装と、外部サービスで実際にどう表示されるかは別です。

役員の記録の検索は同じ自治会の中に絞り、年・種類・相手で探して元の資料に戻れます。全文索引と、短い語を本文から探す処理を使います。終わったものについてAIに聞く機能は、同じ自治会の記録の断片を根拠として渡します。[検索の処理](../src/archive/search.ts)にあります。

## 4. 資料から住民に知らせるまで

1. 写真、ファイル、短い文を受け取り、元の資料を保存します。
2. 写真やPDFを読み取り、どの準備の資料かを選びます。分からないものは「届いたもの」に残します。
3. 既存の内容と照らし、変わったところや質問を記録します。
4. 役員が「住民へのメッセージを作る」から、何を伝えるか（行事の案内や宣伝、手伝いの募集、連絡事項、終わった報告）と、どの準備のことかを選びます。準備に集まった日時、場所、締切などが入った下書きが開き、役員が直します。チラシなどの画像は、手元から足すか、届いた写真から選びます。紙の見え方もここで開けます。
5. 人が知らせる操作をすると、その時点の内容を保存し、住民向けのページ、実行委員と班長のページ、印刷用ページに出します。自治会のLINEで送るかは、四つのどれでも、知らせるたびに役員が選びます。送るときは、画像と、題・日時・場所・返事のページのURLの短い文を送ります（友だちに追加した人だけに届きます）。
6. 紙、Web、電話などの返事を受け、変更があれば直して知らせ直します。
7. 実施後に報告を書いて終わりにし、記録から次の仕事を始めます。

紙のQRや紙の番号は、元の準備と知らせた内容に戻るために使います。下書きの紙は、知らせたあとの紙と区別します。

写真は運営の経緯の確認と報告・印刷に使うため、縦横の比を保って長い辺を2400pxまでに整えます。役員と班長の画面ではブラウザ内でJPEGにして送ります。ブラウザで整えられなかった写真や、自治会のLINEに届いた写真は、保存前にCloudflare Imagesのbindingで同じ大きさ・品質85へ整えます。変換に成功した写真は一つだけR2に保存し、大きい写真や読み取り専用の写しは残しません。読み取りも、後日の読み直しも、保管した写真を使います。変換に失敗した写真はそのまま残し、読めなかったところについての質問に回します。

受付の上限は30点、1点25MB、合計80MBで、写真を整えたあとのバイト数で数えます。同じ写真の照合は変換前のSHA-256を使い、ブラウザからは写真と一緒にその印を送ります。この印（ハッシュ）は、ログインや準備の選択には使いません。

## 5. Claudeが行う仕事

### 資料を読む処理と、準備の中身と照らす処理

写真やPDFの読み取りは、Anthropic Messages APIへの一回の呼び出しで、決めた形式の結果を得ます。Word、Excel、PowerPoint（古い形式の .doc、.xls、.ppt も）は、AIを通さず、ブラウザかアプリが段落と表に取り出して同じ形の読み取りにします。読み取った内容を準備の中身と照らす仕事、下書きや報告を作る仕事にはClaude Managed Agentsを使います。

Managed Agentsには、MCP経由で次の五つの機能を渡します。

- 準備中のものの一覧を読む（list_open_projects）
- 準備の状態を読む（get_project_state）
- 読み取った内容を読む（get_reading）
- 変わったところを書く（write_change）
- 質問を書く（write_question）

どの機能も、最初のメッセージで渡した受付の番号（コードではticket）を引数に取り、その一回の入力の範囲でしか読み書きできません。セッションごとに上限の金額を決めています。自治会ごとに、Managed Agentsの代わりにMessages APIで同じ機能を回す予備の経路もあります。

入力や仕事ごとに短いセッションを開き、前の会話を持ち越す代わりに保存した状態を読みます。エージェントには元の資料そのもの、自由なファイル操作やシェル、住民に知らせる操作を渡しません。資料の中の文は、AIへの指示ではなく資料として扱います。

ほかに、Messages APIの一回の呼び出しで次の仕事をします。候補の中から準備を選ぶ（候補に無い物は作らない）、中身が少しだけ違う二つの資料を比べる（[src/ai/compare-originals.ts](../src/ai/compare-originals.ts)）、LINEで送られた写真だけでは分からないことがあるときに、送った人に聞く一問の文を作る（[src/ai/clarification.ts](../src/ai/clarification.ts)。送る相手、時刻、回数はアプリが決め、一日3問まで）。

### モデルとAnthropicへの認証

読み取り、準備の中身との照合、下書きにはclaude-sonnet-5-5、候補から準備を選ぶ処理にはclaude-haiku-5-5を使います。製品内ではOpusを使いません。Anthropicへの認証は、固定のAPIキーを置かず、Workload Identity Federationで短い期間のトークンを得る構成です。

[読み取り](../src/ai/read.ts)、[セッション](../src/ai/session.ts)、[MCP](../src/ai/mcp.ts)、[モデルと認証](../src/ai/anthropic.ts)に実装があります。

### AIが使えないとき

知らせた案内、返事の受付、記録、印刷は保存済みの内容を使います。役員は手で下書きを直して知らせることもできます。AIが止まっている間も、これらは使えます。

## 6. 自治会のLINE、返事、写真

自治会のLINE（LINE公式アカウント）は運営者が自治会ごとに用意し、受け付けと通知に使います。住民がWebや紙で返事をするのに、友だち追加を必須にはしません。自治会のLINEの一斉送信を使わずに住民向けのページと紙へ知らせることもできます。

役員のLINEグループに自治会のLINEを入れると、グループに貼った写真や連絡がそのまま届きます。役員がグループの投稿を別の画面へ移し直す手間を作らないためです。届いた物は、トークと話題ごとに送られた順の時系列で役員画面に出ます。送った人は、LINEの表示名が取れる限りその名前で、取れない人は自治会の中で決まった番号（「個別に送ってきた方 1」「グループで送ってきた方 2」など）で呼びます。名前は送った人を見分けるためだけに使い、住民向けのページと紙には出しません。

写真をどの準備に入れるかは、紙のQRや番号、自治会のLINEからの質問への答え、撮り直しのように、はっきり結び付く物がある場合は、それで決めます。送られた場所、直前の写真、時期だけでは決めません。AIが判断するときは、同じトークの前30分の文と写真（合わせて20件まで）、後10分の文、準備中のもののやることと日付を比べます。自信がなければ「届いたもの」に残し、後続の文を待っても分からない場合は写真を引用して一問聞きます。

前後の文は、写真をどの準備に入れるかを考えるために一時的に使い、判断後に消します。別の未解決の写真にも必要な文はその判断まで、長くても1日を上限に保持する作りです。別のトークの文は使いません。写真の受け付けと保存はAIの判断失敗でも残します。

世帯の出欠の返事と作業の連絡を分け、問い合わせへの返事は役員が書きます。AIが住民への返事を作ったり、運営上の判断を代わりに行ったりしません。本物のLINEでの文と写真の受信記録はありますが、グループや質問・返事を含む全体の実機確認は別に必要です。

写真は役員の範囲と、実行委員と班長のページで扱います。届いた写真を住民向けのページに自動で載せることはせず、住民に見せる画像は、役員がメッセージに付けると選んだ物だけです。

## 7. 基盤、保管、復旧

| 技術 | 役割 |
|---|---|
| TypeScript、Cloudflare Workers、Hono | 画面、API、受付と処理。WorkersがHTMLを返す |
| Cloudflare D1 | 準備の状態、返事、知らせた記録などを保管する |
| Cloudflare R2 | 元の資料と日次の写しなどを保管する |
| Anthropic Messages API、Managed Agents | 読み取り、準備の中身との照合、質問と下書き |
| LINE Messaging API | 文や写真の受け付け、通知と役員からの返事 |

日次の写し、自治会の書き出し、消去の処理があります。写しのJSONと、R2にある元の資料ファイルは別のものです。復旧には両方の保管と確認が必要で、写しを作る処理があるだけで復旧できると断定しません。

[写しからの復元試験](../test/snapshot-restore-flow.test.ts)は、日次の写しを[snapshot-to-sql.mjs](../scripts/snapshot-to-sql.mjs)でSQLにし、隔離した空の試験用の自治会へ戻します。元の資料ファイルも戻し、役員画面、紙の番号、運営者への問い合わせの読み取りと全文索引の作り直しを確認します。実際のD1・R2へ戻す操作はこの試験に含みません。

[自治会をまたぐ静的検査](../scripts/check-ward-scope.ts)はSQLとR2参照を調べ、自治会で絞られていない読み書きを見つけます。運営者の画面や自治会を決める入口など、全ての自治会を扱う必要がある箇所は理由つきで管理します。[試験](../test/ward-scope.test.ts)ではわざと絞り漏れを足して検出を確認します。静的検査だけで、実行時のすべての情報の流れを保証するものではありません。

個人情報の利用目的、委託の根拠と契約、閲覧範囲、保管期間、バックアップ、削除、障害対応は、運営者が実運用の前に確かめて自治会に説明する必要があります。

写真の保管対象は、運営の確認と報告・印刷のために大きさを整えた写真です。変換に成功したときは、撮影したままの大きい写真を別に残しません。変換に失敗した写真は受け取りを止めず、そのまま保管します。閲覧の範囲と消す道は、ほかの元の資料と同じです。
