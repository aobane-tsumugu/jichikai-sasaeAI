# SasaeAIの採用方針と自治会別費用管理

更新日：2026年11月17日

**状態：採用する設計方針。今回の変更は文書への反映であり、DB移行、API接続の変更、費用管理画面、予算制御を実装・配備したことを示さない。**

この文書は、共用LINE、インフラ、データ分離、認証、AI処理、利用量・費用管理についての変更後の正本とする。[CLAUDE.md](../CLAUDE.md)の利用者負担・公開判断・情報保護の原則を守る。[DESIGN.md](DESIGN.md)、[README.md](../README.md)、[RUNBOOK.md](RUNBOOK.md)に残る2026年11月8日時点の実装説明と異なる技術・運用方針は、この文書を採用する。旧実装の説明を、新しい要件や実装完了の根拠として使わない。

## 1. 判断の基準

- 役員に分類、マスキング、保存先・AIモデルの選択、AI出力の全件点検を求めない。費用削減のために役員・住民の作業を増やさない。
- 住民にSasaeAIへの登録を求めず、住民向けAI対話を設けない。紙とWebを同じ知らせた内容から作り、回答を二度数えない。
- AIの推測を決定として扱わず、人が知らせる。遅れた処理結果で人の修正や知らせた内容を上書きしない。
- AI障害・予算到達でも、知らせた内容の閲覧、Web回答、手入力、手動での下書き・公開、記録、印刷を使えるようにする。
- 分離は現在の情報保護、処理待ち、復旧範囲、運用費から決める。既存構成、特定の提供者・モデル、無料プランへの収容を維持すること自体を目的にしない。

## 2. 採用する基盤と分離単位

| 対象 | 採用する構成 |
|---|---|
| Cloudflare | SasaeAI用アカウントを基本とする。アカウントを流用する場合もサービスのドメインは分ける |
| アプリ | TypeScript、Workers、Honoを共用し、スマホで軽く使えるHTMLを返す |
| Workersプラン | 本番はPaidを基準とする。最低月額5米ドルはアカウント全体の基盤費で、自治会ごとの契約費ではない。従量費・外部サービス費は別 |
| 業務データ | 自治会ごとにD1のDBを分け、同じスキーマを適用する |
| 元の資料・添付 | 自治会ごとに非公開のR2バケットを分ける |
| バックアップ | 自治会ごとの別バケット等に分け、通常アプリからバックアップを削除できる権限を外す |
| 共通管理 | 認証、所属、接続先、資源の対応表、本文を含まない利用量・予算管理を共通管理DBに置く |
| 定期処理 | 受付・定期実行・Workflowsを共用し、自治会別のジョブと同時実行枠で動かす |
| ドメイン | サービス全体で独自ドメインを一つ使う。自治会ごとの取得は不要 |

D1の同じDB内ではSQLの処理待ちとDB全体の復旧単位が共通になるため、同じDB内の自治会別テーブル方式は採らない。自治会別DBにより、選択済みDBでの条件漏れによる影響、処理待ち、復旧の対象を自治会内に限定しやすくする。R2の分離は権限・一括操作・復旧の範囲を明確にするためであり、分離だけで応答時間が短くなるとは主張しない。[D1の方式](https://developers.cloudflare.com/d1/reference/faq/)、[復旧単位](https://developers.cloudflare.com/d1/reference/time-travel/)、[R2の権限](https://developers.cloudflare.com/r2/api/tokens/)を根拠とする。

分離単位は自治会であり、役員グループ、実行委員会、PJ、共用LINE公式アカウントごとにDBを増やさない。自治会内の公開・PJ・役員の閲覧範囲は別に制御する。共用アプリや管理者権限の侵害まで自治会別DB・バケットだけで遮断できるとは扱わない。

自治会の追加時は、DB・バケットの作成、スキーマ適用、Workersへのbinding設定、対応表の登録を運営側で自動化する。スキーマの版を管理し、更新失敗を自治会ごとに把握する。通常のSQL実行ごとにCloudflare管理APIを呼ぶ構成にはしない。各自治会のDB・バケットは実在するbindingへ対応させ、存在が確認できていない動的取得APIを前提にしない。

## 3. 自治会を決める入口と情報の境界

認証済みの所属・権限、または登録済みの「LINE公式アカウントの識別子＋グループID」から自治会を決める。住民の自治会選択は配信先・公開ページの選択であり、役員権限や非公開資料の閲覧権ではない。画面から渡された自治会IDやAPI接続IDをそのまま信用しない。

業務処理へは選択済みのDB・バケットを渡し、全自治会の資源や管理用認証情報を渡さない。ジョブ、検索、キャッシュ、AIへ渡す資料、返ってきた結果にも自治会の帰属を持たせる。自治会共通の価格表など、全体設定の行に架空の自治会IDを付ける必要はない。

非同期結果は、提供者に応じた署名検証または認証済みの取得経路で発信元を確認し、記録済みの接続ID・提供者のrequest_id等から発注したジョブと自治会を照合する。結果内の自治会IDだけで保存先・費用帰属を決めない。対応する発注を確認できない結果は自動反映せず、照合待ちとして扱う。

共通管理DBには認証・所属の情報もあるため、個人情報がないとは扱わない。資料本文、名簿、回答本文、AIの全文入力を共通の費用台帳へ集めない。認証・権限と費用台帳の正本は、自治会の業務DBを復旧する操作と一緒に過去へ戻さない。DBの復旧だけでR2の削除済みファイルも戻るとは扱わず、資料と記録の整合を確認する。

## 4. 共用LINEと住民・役員の使い分け

### 共用するアカウント

市の既存配信システムから独立した、自治会向けの共用公式アカウントを複数用意する。市公式アカウントの流用・外部Webhook転送、自治会別の受信と市アカウントからの配信を組み合わせる方式は採らない。1アカウントあたり月約15,000通以内を運用上の目安とする。これはLINEの正式なプラン上限・無料枠の名称ではない。

共用公式アカウント内でも、配信対象は自治会ごとに選ぶ。アカウント全体へのbroadcastを自治会別配信の代用にしない。自治会別の配信量・上限と、公式アカウント全体の契約枠・予約済み通数を両方管理する。題名に「雨」等が入ることを理由に、送信対象・予算確認・送信可否を迂回しない。

### 役員・実行委員の仕事

通常のLINEアカウントで作成した役員・実行委員会・PJ等のグループへ公式アカウントを招待し、接続したグループから文・写真・資料を受け付ける。役員業務のLINE受付は接続したグループに統一し、Web役員画面からの資料受付も保つ。SasaeAIから通常のLINEグループを自動作成できる前提や、未実在の「SasaeAIグループ作成QR」を置かない。

役員画面で管理する自治会共通の接続コードを、対象グループへ投稿する。署名を検証したWebhookに含まれる公式アカウントとグループID、投稿されたコードから、接続先の自治会を記録する。初回にグループの用途・対象PJをLINEで聞き、そのグループの設定として保存する。用途の自由文を毎回分類し直さない。

コードはグループごとに発行せず、10分・7日等の定期的な自動失効も設けない。新規接続を止める・コードを変更する操作と履歴を用意し、変更だけで既存グループを切断しない。コードを役員ログインや非公開記録の取得権として使わず、試行回数制限・推測困難な値・接続履歴・個別解除で守る。既存の他自治会への接続をコード投稿だけで上書きしない。役員招待・ログイン復旧リンクの有効期限とは別の仕組みとする。

### 住民向けの配信と回答

自治会全員が参加するLINEグループは作らない。住民は共用公式アカウントの個別トーク、リッチメニュー、LIFF等から自治会を選び、知らせとWebの回答画面へ進む。選択中の自治会を画面上で明示し、リッチメニューを切り替える場合も同じ選択状態に合わせる。自己申告の所属と、確認済みの役員権限を混同しない。

回答はWeb・LIFFの定型入力と、紙・電話の回答を同じ集計へ入れる。住民の個別トークの自由文をAIで読んで出欠へ変換する処理は実装対象から外す。問い合わせの返事は役員が書き、AIが住民へ自動回答しない。問い合わせを役員へ知らせる場合も配信の集約・予算制御の対象とし、受信のたびに有料通知を増やさない。

## 5. AIと実行時刻

LINEの文・ファイルは受信時に取得・保存する。AIで読む処理は、短い時間に届いた投稿をまとめ、差分・既存の読み取り結果を再利用して定期的に行う。ログイン、公開済みページ、回答保存、通常の集計はAIを呼ばない。[LINEの受信仕様](https://developers.line.biz/en/docs/messaging-api/receiving-messages/)に従い、本文や添付を後で必ず取り直せるとは扱わない。

通常のAI処理は永続化したジョブと直接API呼び出しで行う。定期実行で扱える処理はその範囲にとどめ、長い待機や段階的な再実行にはWorkflowsを使う。Claude Managed Agentsを主経路とする規定と、長い仕事をwaitUntilだけで完了させる構成を外す。Queues・Durable Objects等を一式で追加することは要件にしない。

Claude（Haikuを含む）、OpenAI（Luna等）、Jev、Decisions API等を比較対象にし、処理ごとの品質と完了までの総費用で採用経路を決める。SDK・Sonnet・Haikuの用途を固定せず、特定の高性能モデルを一律禁止・常用しない。分類だけの別APIを呼ぶ方が総額を増やす場合は追加しない。利用者にモデルを選ばせず、モデルID・単価・許可経路は検証した設定として管理する。品質や削減額を実測前に断定しない。

定期実行そのものがAPI単価を下げるとは扱わない。回数・入力量の削減と、締切に合うBatch等の料金方式を組み合わせる。役員が明示した作業は優先できるが、予算制御は迂回しない。写真の結び付けに一時利用する会話の最長1日という既存の保持条件を、Batchの都合で延ばさない。必要な判断を保持期限内に行い、後段には必要な構造化結果を渡す。

自治会ごとの同時実行枠と、公平に取り出すジョブ処理を持ち、一つの自治会の大量処理で他をすべて待たせない。再開時には人の修正・公開の版を照合する。AIの機能は対象の受付・自治会・PJに限定し、任意SQL・シェル・住民への送信を渡さない。

## 6. 認証とドメイン

役員のパスキーを推奨し、必須にはしない。ログイン状態の維持、既存のLINE・メール・IDとパスワード、本人確認を伴う復旧と組み合わせる。弱い復旧経路でパスキーの保護を無効にしない。LINE内ブラウザを含む対応を実機未確認のまま保証しない。役員の自動除籍・任期による自動失効は追加しない。

端末へ秘密鍵ファイルを配るデバイス証明書方式は標準にしない。役員にCloudflareのアカウント・証明書・APIキーの管理を求めない。サービスのURLとパスキーの認証先を固定するため独自ドメインを一つ採用する。無料の提供サブドメインでは一律にパスキーが使えない、という理由にはしない。

## 7. 自治会別に計測する利用量

共通基盤の費用を一つにまとめても、利用量の帰属は自治会ごとに残す。自治会の業務処理には必ずward_idを付ける。未接続のLINE受信、共通管理、障害対応等は共通運用として記録し、推測で特定自治会へ課金しない。

| 費目 | 自治会別に残す数字 | 取得・区別の方針 |
|---|---|---|
| AI | 提供者・モデル・用途別の実行数、成功・失敗・再試行、提供者が返す入出力・キャッシュ等の課金対象使用量 | API応答・利用明細と対応付ける。課金区分が重複するトークンを二重に足さない。応答未取得は推計・未照合として残す |
| LINE | 送信方法別の要求数、対象人数、計上見込通数、失敗・再試行、公式アカウントの使用量との照合差 | HTTP呼び出し数や吹き出し数をそのまま課金通数にしない。replyとpush等を分け、個別の到達数を取得できない部分は推計と表示する |
| D1 | DB・索引の保存量、読み取り行数、書き込み行数 | 自治会別DBのメトリクスや戻り値を集計する。共通管理DBの分は共通費として区別する |
| R2 | 原本とバックアップそれぞれの保存量・保存期間、オブジェクト数、操作種別の回数 | バケット別のメトリクスを定期取得する。月末時点の容量だけをGB-monthと同一視しない |
| Workers・Workflows等 | 自治会に帰属する処理回数・ジョブ数・取得可能な実行資源量 | 実測できる項目と、リクエスト数等による按分を分ける。外部APIの待ち時間をCPU使用量とみなさない |
| 画像処理等の外部サービス | 変換数・処理単位・外部使用量 | AI以外の有料APIも同じ接続・費用管理を通す |

D1の戻り値にはrows_read、rows_written、size_after等があり、R2にはバケット別の操作・保存量のメトリクスがある。これらを使い、全SQL・全アクセスのたびに別の費用イベントを同期書き込みする構成を避ける。高頻度の基盤利用量は時間・日単位に集計し、保存期間内に回収する。有料外部APIの試行・予算予約は取りこぼさず残す。[D1の戻り値](https://developers.cloudflare.com/d1/worker-api/return-object/)、[R2の計測](https://developers.cloudflare.com/r2/platform/metrics-analytics/)、[LINEの通数](https://developers.line.biz/en/docs/messaging-api/pricing/)を参照する。

各数値は「直接計測」「規則による按分」「推計」「未照合」を区別し、取得元・対象期間・更新日時を持たせる。分析用メトリクスの遅延や欠落をゼロ利用として埋めない。計測の保存・処理費用も共通費として把握する。

## 8. 原価、共通費、自治会負担額

次の四つを別々に保持する。

| 区分 | 意味 |
|---|---|
| 利用量 | 自治会がどれだけ使ったか。無料枠内でも記録する |
| 提供者への原価 | 適用単価からの見積額と、提供者明細に照合した額。見積と確定を分ける |
| 共通費の按分 | 基盤・ドメイン・共用LINE等の費用を、決めた規則で自治会へ割り当てた額 |
| 自治会の負担・請求額 | 契約した料金・控除・按分・直接支払の扱いから計算する額。提供者原価と同一とは限らない |

Workersの最低料金、D1・R2の包含枠・無料枠はCloudflareアカウント全体で扱う。自治会別DB・バケットにしても無料枠を自治会ごとに重ねない。APIやLINEの割引・包含枠も、その契約単位で適用する。原本の写しも保存量へ含める。通常単価を掛けただけの見積を、提供者の実請求として表示しない。

按分は費目・契約単位ごとに規則を持つ。固定費は対象自治会と利用日数を基にした均等按分、従量費は帰属する使用量による按分を基本とし、別の負担方式も設定で扱えるようにする。無料枠・割引を誰に配るか、端数、最低料金、為替、税の扱いも規則の版に含める。接続を早く使った自治会だけが無料枠を消費した扱いにせず、採用した配賦規則で精算する。

期間ごとに「自治会へ帰属する原価＋共通運用分＋未帰属・調整分」が提供者側の原価へ照合できるようにする。見込と確定の差を消さず、締めた期間は上書きせず調整記録を残す。共通費の規則・対象自治会の変更には適用開始日と履歴を持たせ、月中の変更を過去へ黙って適用しない。

自治会が直接支払うAPI費用は利用量・総費用の表示に含めても、SasaeAIからの請求へ重ねて計上しない。課金・決済サービスや自治会会計全体を今回の要件へ追加しない。まず利用量と明細を出力でき、按分・従量課金の根拠を再計算できる設計にする。

## 9. 費用台帳と設定の最低項目

| 記録 | 主な項目 |
|---|---|
| 外部処理・利用量 | ward_id、job_id、operation_id、attempt_id、用途、提供者・モデル、実行状態、提供者のrequest_id、使用量、計測区分、発生日時 |
| 原価と負担先 | 接続ID、契約・project/workspace、支払者、課金単位、実際の認証設定の版、単価・為替・税の規則の版、原通貨、見積・照合額、提供者の請求期間 |
| 予算と予約 | 自治会、予算期間、対象費目、上限、維持費等の確保額、処理前予約、精算額、未確定額、状態、変更者・理由・日時 |
| 月次集計・按分 | 自治会別の使用量、直接費、共通費按分、外部への直接支払分、SasaeAIの請求対象、控除・調整、規則の版 |

金額は通貨付きの固定精度または最小計算単位の整数で保持し、円未満を処理ごとに切り捨てない。表示の丸めと予算計算を分ける。予算期間は日本時間の暦月を基本とし、提供者の請求期間が異なる場合も元の期間を保持する。

台帳の正本は、自治会の業務DBと別の復旧単位である共通管理領域に置く。業務DBを戻しても支出済み費用・予約・失効済み接続を復活させない。台帳には資料本文、個人名、APIキー本体を入れない。保存する識別子にも閲覧権限を適用し、各自治会には自分の明細だけを返す。

## 10. 自治会別の上限と実行前予約

自治会ごとに、月額の負担上限、SasaeAI経由のAPI利用予算、AI等の費目別上限、1処理の最大額、LINE通数、保存容量・受付量、同時実行数を設定できるようにする。通常は運営側の初期値を使い、役員が毎回設定しない。金額の0はその追加支出を許さない意味とし、未設定を無制限として扱わない。

月額の総枠から、契約した固定費・共通費の配賦見込、保存・回答受付・バックアップ等の維持費見込、未確定費用の余裕を先に確保し、残りを新しい有料処理へ使う。上限が既存の必要費用を下回る設定では「その額で維持できる」と表示せず、新規支出を止め、必要額との差を権限者へ知らせる。

原価管理の予算は提供者原価で、自治会負担の予算は契約した料金・按分規則による負担額で計算する。各上限に自治会の直接支払分を含むかを明示し、異なる費用基準の金額を同じ残高へ混ぜない。維持費・配賦見込が確定したときは、対応する確保額を精算額へ振り替え、二重に控除しない。単価・按分規則・対象自治会の変更は適用開始時点から確保額と残予算へ反映し、発注済み予約を消さない。

処理前の判断は、同じ予算期間・通貨で次を満たす場合に限る。

> 精算済み使用額＋維持費等の確保額＋処理中・未確定の予約額＋今回の最大見積額≦設定上限

実行は次の順序とする。

1. 自治会・用途・認証済み権限を確かめ、許可されたAPI接続と単価の版を選ぶ。入力・出力・反復・再試行の上限を含め、今回の予約額を計算する。
2. 自治会の総枠・費目枠と、共用契約やLINE公式アカウントの枠を確認し、必要な枠を共通台帳側で一括して予約する。すべて成立または不成立にし、一部の枠だけを消費した状態で外部処理を開始しない。残額を読んでから無条件に減らす実装にせず、同時実行が同じ残額を使わないようにする。
3. 予約の存在確認に加え、同じ処理・試行の実行権を条件付き更新で一つの実行だけが取得する。実行直前に接続停止・権限変更を確認する。外部呼び出しの開始後に状態が不明になった試行を未実行へ戻して再発注しない。業務DBと共通台帳をまたぐ処理が一つのトランザクションになるとは仮定せず、処理番号と状態で再開・照合できるようにする。
4. 実際の使用量で精算し、未使用の予約を解放する。費用と結果が保存済みなら、業務DBへの反映失敗では結果反映だけをやり直し、外部APIを呼び直さない。結果を失い再発注が必要な場合も前回費用を残し、別試行として新しく予約する。次の工程・追加の再試行には残予算を再確認する。見積上限を安全に定められない処理を無制限に自動開始しない。

画面からの依頼、定期処理、Batch、再実行、代替モデル、役員への有料通知をすべて同じ入口へ通す。APIキーや提供者を替えても自治会の予算はリセットしない。提供者側の上限も補助として使うが、設定の範囲や反映遅延があるため、SasaeAI側の予約を省略しない。

## 11. 上限到達、失敗、再試行の扱い

- 上限到達時は、新しい有料AI処理・有料送信等を保留し、理由と再開条件を記録する。上限を毎回の作業承認に置き換えない。
- 公開済みページ、回答保存、手入力、手動の下書き・公開、印刷、既存記録へのアクセス、必要なバックアップは維持枠で継続する。LINE送信の保留とWeb公開の成功を別々に表示する。
- 受信資料は既定の容量・件数・速度の範囲内で先に保存し、AI処理を待機できるようにする。無制限の受信を保証しない。保存枠に入らないものを受付済みと表示せず、既存資料を予算到達だけで自動削除しない。
- 通信失敗でも相手側で課金された可能性がある処理は未確定とし、時間切れだけで予約を解放しない。対応するAPIでは同じ冪等キー等で重複を防ぎ、非対応APIで二重課金が絶対にないとは扱わない。
- 再試行はattempt_idを分け、原価が発生した試行をすべて残す。運営側の不具合による再処理を自治会へ請求するかは負担規則で分ける。Webhook再送・再集計は同じ計測イベントを二重計上しない。
- 月をまたいで完了した発注済みの試行は、その試行の元の予約期間に精算し、提供者の請求期間も別に残す。未発注と確認できる待機ジョブ、新しい工程、追加の再試行は、実行時点の予算期間で判定し、古い未使用予約を解放したうえで必要な予約を取り直す。上限を引き下げても発注済み費用と予約は消さず、新規処理を止める。
- 台帳・予算確認が使えない間は新しい有料処理を始めず、AIを使わない基本機能を継続する。DB復旧後の再処理も台帳と照合してから行う。

**追加処理の予算制御と、自治会へ請求する上限、提供者からの実請求額は同一ではない。** 保管費、固定契約、未確定の外部処理費はAI停止後も残る。自治会負担上限を超えた差額を、その自治会へ自動請求したり、他の自治会へ黙って付け替えたりしない。差額は運営側の負担・未精算として区分し、追加負担が必要な場合の契約上の扱いは権限者による上限変更と分けて記録する。

自治会が直接契約したAPIでは、SasaeAIが制御できるのはSasaeAI経由の実行である。同じ契約を他のシステムで使った費用や、提供者が遅れて確定する額まで、このアプリの上限で完全に止められるとは約束しない。

## 12. 自治会ごとにAPIを分けられる接続管理

既定は運営者が用意した接続を使い、役員にAPI契約を必須としない。そのうえで、自治会・サービスごとに次の方式を選べる設計にする。

| 接続方式 | 設計上の扱い |
|---|---|
| 運営者の共用契約・共用接続 | アプリ側で自治会別に計測し、予算を分ける |
| 運営者の契約内の自治会別project/workspace・認証情報 | 提供者側の区分と自治会を対応付ける。上位契約の請求・利用枠が共有される範囲も残す |
| 自治会別契約・自治会提供の接続 | 支払者を自治会として管理し、SasaeAIの請求に同じAPI費を重ねない |

APIキーが違うだけで、請求書、残高、レート制限、データ保管範囲が独立するとは判断しない。接続設定には、提供者、許可された送信先、契約アカウント、project/workspace、課金単位、利用制限の共有範囲、支払者、許可された自治会・用途・モデル、認証方式、秘密保管先の参照、設定の版、有効・停止状態を持たせる。APIキー、短期トークン、Workload Identity Federation等を提供者に合わせて扱う。

秘密値はWorkersのsecrets等の管理された秘密保管先に置き、平文で通常のD1、R2の業務バックアップ、ジョブ、ログ、ブラウザへ出さない。資源作成・請求照合等の管理用資格情報も通常の推論用と分ける。住民の投稿や資料内の指示で、API接続・任意URL・請求先を変更できるようにしない。

ジョブには接続・課金先・予算・方針の版を記録し、実際の試行には使った認証情報の世代を記録する。同じ提供者・契約・project/workspace・データの範囲・費用負担先を保つ鍵更新は可能にする。これらの範囲を変える場合は接続変更として記録し、アクセス権・未確定費用・予算予約を確認する。待機中・再試行中の仕事を別の課金範囲へ黙って移さない。失効は実行直前にも確認する。接続を変えて再実行する場合は、前の実行・未確定費用を照合し、必要な予約を取り直す。

独自接続が失敗したときに共用接続や別自治会の接続へ自動で逃がさない。代替経路はあらかじめ許可された接続・費用負担・残予算の範囲だけで使う。別モデル・別提供者へ切り替えた事実と費用帰属を残す。

外部API上のファイル、会話、検索対象、明示的キャッシュ、BatchのIDも自治会・接続・提供者側projectに結び付ける。Batchは自治会・接続設定ごとに作り、異なる契約・認証情報を混ぜない。自治会の資料や回答を別自治会へ再利用するキャッシュを作らない。共通の指示文の再利用とは区別する。

AI用APIの区分とLINE公式アカウントの区分は別に管理する。独自のAI接続を使う自治会が、ほかの自治会とLINEを共用してよい。どちらかの変更で、もう一方の接続や費用負担を自動変更しない。

## 13. 利用量・費用を見る画面

費用を扱う権限のある役員とSasaeAIの運営者は、自治会ごとの次の内容を見られるようにする。

- 当月と過去の利用量、費目別の見積額・照合済み額、処理中・未確定の予約額、残予算、保存量、LINE通数。
- 共通費の按分額・計算根拠、適用した規則と期間、自治会が外部へ直接支払う額とSasaeAIの請求対象。
- 上限に近付いた通知、保留された処理と理由、上限・接続・負担方式の変更履歴。
- 月次明細と集計のCSV出力。個人情報やAPIキーを明細へ含めない。

費用閲覧・上限変更・API接続変更の権限を分け、住民や一般の実行委員へ出さない。上限・配賦・接続変更は変更者と適用開始時点を記録する。日常作業へ価格の選択や都度承認を差し込まず、API接続の運用を役員の必須作業にしない。

## 14. 現行実装から変更する箇所と受入条件

現行の共用D1、R2の自治会接頭辞、自治会ごとの公式LINE、Managed Agents主経路、固定モデル、個別トークの自由文回答処理は、この方針に合わせたコード変更が必要である。現行RUNBOOKに新構成の操作手順があると扱わない。

実装時に確認する主要な条件は次のとおりとする。今回の文書更新でこれらの試験が済んだとは報告しない。

1. 同じ共用LINEやWebからでも、保存・検索・AI入力・結果・費用が正しい自治会に帰属し、他自治会の非公開データを返さない。
2. DB・バケットの追加と共通スキーマ更新を役員の手作業なしで行え、自治会単位の復旧で他自治会の業務や支出・認証の正本を巻き戻さない。
3. 並行する処理、再試行、重複Webhook、月跨ぎ、上限変更でも二重発注・二重計上を防ぎ、予約と実行権を得ない有料処理を開始しない。別DB間の更新失敗では、保存済み結果の反映をやり直すだけで外部APIを呼び直さない。
4. 上限到達やAPI停止でも基本機能を使え、Web公開とLINE送信結果を取り違えない。
5. APIキー更新・提供者変更で残予算が復活せず、失効した接続や未許可の課金先へ切り替わらない。
6. 自治会別明細と共通運用・調整分を提供者明細へ照合でき、外部への直接支払分を重ねて請求しない。
7. 費用・利用量の参照と設定変更に権限を適用し、資料本文・認証情報を費用ログへ漏らさない。
